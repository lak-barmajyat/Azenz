# Database Rules — Azenz

## Responsibilities

| Path | Responsibility |
|---|---|
| `database/models/` | SQLAlchemy ORM models defining the intended schema. |
| `database/migrations/` | Alembic configuration and migration history. |
| `database/schema/` | SQL reference snapshots and demo-data scripts. |
| `database/engine.py` | Database engine and connection configuration. |
| `database/session.py` | Session lifecycle and `@with_session()` decorator. |
| `database/setup.py` | Database initialization and setup. |
| `database/legacy/` | Historical backups. Never read, modify, or use. |

## Database Access
- Use SQLAlchemy for application database operations.
- Keep each window's database queries in its `model.py`.
- **Always use `@with_session()`** for feature database operations, following its existing session and transaction behavior.
- Never create ad-hoc database connections or sessions in feature code.
- Database setup and Alembic migrations manage their own connections; `@with_session()` does not apply to them.
- Never share SQLAlchemy sessions across threads.

## Schema and Migrations
- **Request approval before modifying database structures**, including tables, columns, indexes, and constraints.
- SQLAlchemy models and Alembic migrations are the source of truth.
- After approval, update ORM models and generate an Alembic migration.
- Manually review autogenerated migrations before applying them.
- Never modify an already-applied migration; create a new one.
- Never use `Base.metadata.create_all()` to update an existing database.
- Request approval before modifying demo data.

## Migration Commands

| Command | Purpose |
|---|---|
| `make create-migration` | Autogenerate an Alembic migration. |
| `make apply-migrations` | Initialize the configured database, apply migrations up to `head`, verify the schema, and ensure a Manager account exists. |
| `make show-current-revision` | Show the currently applied migration revision. |
| `make show-migration-history` | Display migration history. |
| `make check-migrations` | Check for pending ORM schema changes. |

- `make apply-migrations` runs `database.setup init`, which calls Alembic `upgrade head`.
- The target database comes from the application's loaded configuration.
- Development uses local MySQL; production uses the configured remote MySQL server.
- Always confirm the target database before executing migrations.
- Never apply production migrations without explicit approval.
- Review autogenerated migrations before applying them.

## SQL Artifacts
- `database/schema/` contains reference SQL and demo-data scripts, not the migration source of truth.
- Do not update SQL snapshots after every migration.
- Update SQL artifacts only when explicitly requested.
- Never use files from `database/legacy/`.

## Quality
- Keep queries simple and efficient; avoid unnecessary database calls.
- Follow project linters and formatters.
- Check migration operations for potential data loss and constraint conflicts.
